# rules.md — нормативные правила проекта «Усадьба Лыково»

Свод проверяемых правил для `lyk-farm`. `AGENTS.md` объясняет «почему» и описывает структуру,
этот файл — «что именно нельзя/нужно». Skills (`.agents/skills/*/SKILL.md`) описывают порядок
работ; при расхождении приоритет у `rules.md` и `AGENTS.md`, а skill правится.

Формат правила: `R-<блок>-<номер>` — формулировка. Нарушение = блокирующий дефект ревью.
Плейсхолдеры: `{Entity}` — StudlyCase, `{entity}` — kebab-case, `{Model}` — имя модели.

## 1. Архитектура и слои (R-ARCH)

- **R-ARCH-1.** Поток страницы: `Route → Controller → Service → Repository → Model → Blade`.
  Поток JSON: `Route → Request → Controller → Service → Repository → Model → Resource → Presenter`.
- **R-ARCH-2.** Каждый слой отвечает только за своё (таблица обязанностей в `AGENTS.md` §4).
- **R-ARCH-3.** Контроллер не содержит запросов к БД, вычислений, валидации, вызовов моделей.
- **R-ARCH-4.** Request содержит только правила валидации, сообщения, атрибуты и `$dtoClassName`.
- **R-ARCH-5.** Модель содержит только `$table`, `$fillable`, `$casts`, связи и скоупы.
  Никакой бизнес-логики.
- **R-ARCH-6.** Resource только отображает данные; запросы к БД и вычисления запрещены.
- **R-ARCH-7.** Общая логика выносится в трейты `app/Traits/*`, а не в хелперы и статические
  «утилитные» классы.
- **R-ARCH-8.** Не переименовывать существующие публичные поля, методы, ключи JSON и коды
  справочников: на них завязаны фронт, сидеры и вёрстка.
- **R-ARCH-9.** Вся бизнес-логика — в сервисах. Вычисления для отображения (формат цены,
  веса, фасовки, склонения, даты, регистр, подписи статусов) выполняет слой отображения
  (Blade/Vue); сервис отдаёт модели, Resource — сырые значения.
- **R-ARCH-10.** Связи моделей называются без префикса `r*`: `season()`, `category()`,
  `products()`; ключи в конфигах и JSON — `snake_case`.
- **R-ARCH-11.** Slug — техническое поле: генерируется на событии модели, не принимается
  из Request и не редактируется с фронта; существующий slug не перегенерируется.
  Resource отдаёт `slug` и `id` как идентификаторы для URL.
- **R-ARCH-12.** Сервис и репозиторий внутри кода работают с моделями и `Collection` моделей.
  Resource отдаёт сырые данные: число, enum-код, массив фактов, строку периода сбора,
  UTC-дату. Вычисленных полей вида `price_label`, `status_label`, `products_count_label`,
  `current_month_label` в контракте нет — их строит слой отображения.
- **R-ARCH-13.** Время в БД хранится и передаётся в UTC. Сервер не применяет часовой пояс
  пользователя, не вычисляет его локальный месяц и не форматирует даты для интерфейса.
  Локальная дата, месяц и часовой пояс — ответственность фронтенда. Исключение — выгрузки
  файлов, где часовой пояс задаётся явно.
- **R-ARCH-14.** Для наборов данных используется `Illuminate\Support\Collection`
  (`map`, `filter`, `sortBy`, `take`, `values`, `groupBy`, `pluck`, `sum`), для строк и
  массивов — `Str` и `Arr`. Нативные `mb_*`, `array_slice`, `array_filter`, `array_map`,
  `array_merge`, `usort` и подобные в коде приложения не используются; массив допускается
  только на границе API (`->all()`, сигнатуры фреймворка/пакета).

## 2. Маршруты (R-ROUTE)

- **R-ROUTE-1.** Страницы сайта — `routes/web.php`; JSON API — `routes/api.php`.
- **R-ROUTE-2.** Справочники не имеют ручных роутов: их генерирует `laravel-handbooks`
  по `config/handbooks.php`.
- **R-ROUTE-3.** Имена действий API: `list`, `detail`, `create`, `update`, `delete`;
  составные — через дефис (`set-active`).
- **R-ROUTE-4.** Чтение — `GET`, изменение — `POST`, удаление — `DELETE`.
- **R-ROUTE-5.** Для собственных JSON-эндпоинтов id передаётся в query (`GET`) или body
  (`POST`/`DELETE`). Path-параметры допустимы только в web-роутах страниц и в роутах
  справочников (контракт пакета).
- **R-ROUTE-6.** Группа middleware выбирается по потребителю: публичные страницы — без
  авторизации; закрытый API — `auth:api` (Passport).
- **R-ROUTE-7.** Новый роут проверяется `php artisan route:list`: нет дублей URI, метод и
  middleware соответствуют ожиданию.
- **R-ROUTE-8.** Slug страницы/сущности — `kebab-case`, совпадает с URL и с ключом в сидерах.

## 3. Валидация и DTO (R-REQ)

- **R-REQ-1.** Валидация только в классах `app/Http/Requests/{Entity}/`,
  наследниках `Laravel\Foundation\Abstracts\AbstractRequest`.
- **R-REQ-2.** `$request->validate()`, `Validator::make()` в контроллере или сервисе запрещены.
- **R-REQ-3.** Каждый Request объявляет `protected ?string $dtoClassName = ...;` — иначе
  `validated()` вернёт массив, а не DTO.
- **R-REQ-4.** Список — пакетный `GetListRequest` + `GetListRequestDTO`; одна сущность по `id` —
  пакетные `GetEntityRequest` + `GetEntityRequestDTO`. Свой Request для этих случаев не создаётся.
- **R-REQ-5.** `Update{Entity}Request extends Create{Entity}Request`; переопределяются только
  отличия (`Arr::except(parent::rules(), [...])` + `'id' => ['required', 'uuid']`).
- **R-REQ-6.** `Update{Entity}RequestDTO extends Create{Entity}RequestDTO` + типизированный `$id`.
- **R-REQ-7.** Enum-поле валидируется `Rule::enum(EnumClass::class)`, не строкой `in:`.
- **R-REQ-8.** Существование FK — `new Exists('{table}', 'id')`; уникальность — `new Unique('{table}', 'slug')`.
- **R-REQ-9.** Сообщения — в `messages()`, названия полей — в `attributes()`.
- **R-REQ-10.** DTO — наследник `Laravel\Foundation\Abstracts\AbstractDto`; свойства `camelCase`
  с явными типами; массивы DTO объявляются через `getDtoArrays()`.
- **R-REQ-11.** DTO не ходит в БД и не содержит логики; преобразование ключей делает `AbstractDto`.
- **R-REQ-12.** `toArray()` DTO используется для передачи данных в репозиторий (ключи `snake_case`).
- **R-REQ-13.** Неизвестные ключи допускаются только осознанно: переопределение конструктора
  с `parent::parseData($data, false)`.
- **R-REQ-14.** Поля, приходящие вложенными массивами, обязаны быть описаны в правилах —
  невалидированные ключи отбрасываются глобально (`$excludeUnvalidatedArrayKeys = true`).
- **R-REQ-15.** Для страниц без формы (MVP) Request-классы не создаются «на будущее».
- **R-REQ-16.** DTO не содержит вычисленных label-полей и отформатированных строк для
  отображения; только сырые значения и enum-коды. Исключение — данные, которые уже являются
  контентом (названия, тексты, имена иконок).
- **R-REQ-17.** DTO сущности для отдачи на фронт не создаётся. Допускается DTO агрегата
  страницы (`app/DTO/{Page}DTO.php`) для сложного ответа из нескольких сущностей; он может
  содержать модели и `Collection` моделей, а его ресурс лежит в
  `app/Http/Resources/DTO/{Page}Resource.php`.

## 4. Сервисы и репозитории (R-DATA)

- **R-DATA-1.** Сервис — `app/Services/{Entity}Service.php`, наследник `AbstractService`,
  только статические методы. Вызов: `{Entity}Service::method()`.
- **R-DATA-2.** Репозиторий — `app/Repositories/{Entity}Repository.php`, наследник
  `AbstractRepository`, методы статические.
- **R-DATA-3.** Модель регистрируется в `AppServiceProvider::$modelList`; репозиторий
  резолвится по соглашению имён.
- **R-DATA-4.** Все мутации — только методами репозитория.
- **R-DATA-5.** Сложные выборки (`join`, `whereHas`, подзапросы, агрегаты, raw SQL) — методы
  репозитория, не сервиса.
- **R-DATA-6.** Жадная загрузка связей (`with()`) задаётся до Resource — N+1 в представлении
  запрещён.
- **R-DATA-7.** `getModel()` вернул `null` → доменное исключение в сервисе, не `null` в ответе.
- **R-DATA-8.** Транзакция открывается в сервисе и закрывается при любом исходе.
- **R-DATA-9.** Общая логика — трейт `app/Traits/Service/`, не хелпер.
- **R-DATA-10.** Простой список — `query()->fromGetListDto($dto, $searchableFields)->paginate()`.

## 5. JSON-ответ (R-RESP)

- **R-RESP-1.** Ответ API — Resource в презентере: `DataResultPresenter` (одиночный),
  `PaginatedDataPresenter` (список).
- **R-RESP-2.** FK `*_id` не выводится напрямую — только через `getRelation()`.
- **R-RESP-3.** Enum — только `getEnum()` / `getEnumArray()` / `renderEnum()`.
- **R-RESP-4.** Ключи ответа — `snake_case`.
- **R-RESP-5.** Связи не догружаются внутри Resource.
- **R-RESP-6.** Нестандартная обёртка — свой презентер в `app/Http/Presenters/`, а не массив
  в контроллере.
- **R-RESP-7.** Страницу рендерит Blade. Данные для Vue-островов, JSON API и любых
  фронтовых потребителей проходят через Resource: модели и коллекции моделей наружу
  не сериализуются.
- **R-RESP-8.** На каждую сущность — ровно один Resource в `app/Http/Resources/{Entity}Resource.php`,
  наследник `Laravel\Foundation\Abstracts\AbstractResource`.
- **R-RESP-9.** Сервис и репозиторий возвращают модели/`Collection` моделей, а не Resource.
  Resource применяется только на слое ответа — в контроллере или агрегирующем page-ресурсе.
- **R-RESP-10.** Агрегирующая страница (например, главная) описывается DTO в
  `app/DTO/{Page}DTO.php`, а её page-ресурс лежит в `app/Http/Resources/DTO/{Page}Resource.php`.
  Page-ресурс собирается из ресурсов сущностей; собственных продублированных полей сущностей
  в нём нет.
- **R-RESP-11.** Resource выводит `id` и `slug` как идентификаторы сущности; `slug`
  не принимается из Request и не редактируется, но фронту нужен для URL.

## 6. Enum (R-ENUM)

- **R-ENUM-1.** Enum — native backed enum + `Laravel\Foundation\Traits\Enum\BaseEnumTrait`.
- **R-ENUM-2.** Значение — `snake_case`, стабильное; переименование только с миграцией данных.
- **R-ENUM-3.** Перевод в `lang/ru/enums.php` для каждого case; формат — как в текущем файле.
- **R-ENUM-4.** Enum, нужный фронту как справочник, добавляется в `config/handbooks.php` → `enums`.
- **R-ENUM-5.** В контроллере `->render()` не вызывается.

---

## 7. Фронтенд (R-FE)

- **R-FE-1.** Blade отдаёт весь индексируемый контент: шапку, `h1`, тексты сезонов, сетку
  каталога, цены, FAQ.
- **R-FE-2.** Vue — только Options API; `vue-router`, Inertia, SSR не используются.
- **R-FE-3.** Один entry-point `resources/js/app.ts` с реестром островов; отдельные бандлы
  на остров не создаются.
- **R-FE-4.** Данные острова приходят пропсами через `data-props`, а не запросом в `mounted()`.
- **R-FE-5.** Острова не вкладываются друг в друга; SEO-контент — вне контейнера острова.
- **R-FE-6.** Общее состояние — модуль-стор (`resources/js/stores/*.ts`), не глобальные
  переменные на `window`.
- **R-FE-7.** Переходы — обычные `<a href>` и маршруты Laravel.
- **R-FE-8.** `prefers-reduced-motion` уважается; без JS страница остаётся читаемой.
- **R-FE-9.** Стили — на токенах `docs/handoff/04-tokens`; шрифты хостятся локально.
- **R-FE-10.** TS strict; данные с сервера типизируются и проверяются zod, если приходят
  не пропсами Blade.

## 8. База данных (R-DB)

- **R-DB-1.** Схема — только миграциями (`php artisan make:migration`).
- **R-DB-2.** Колонки `snake_case`, FK — `{model}_id`, индексы на FK и поля фильтрации.
- **R-DB-3.** VIEW не создаются и не используются.
- **R-DB-4.** Мок-данные MVP — идемпотентные сидеры (`updateOrCreate`), не `insert`.
- **R-DB-5.** Поля модели проектируются сразу под будущую админку: без переименований позже.
- **R-DB-6.** PostgreSQL 15.2; SQL пишется под него (без MySQL-специфики).
- **R-DB-7.** Enum-колонки — `$table->enum('field', EnumClass::values())`; добавление
  значения — отдельная миграция с трейтом `EnumDBCheckAlterable` и вызовом `$this->alterEnum(...)`
  плюс перевод.
- **R-DB-8.** Каждая колонка в миграции имеет `->comment('…')` с назначением поля.
  Для `created_at`/`updated_at` комментарий явно указывает хранение в UTC.
- **R-DB-9.** В `$fillable` модели у каждого поля есть inline-комментарий с человекочитаемым
  названием и назначением.

## 9. Пакеты `vasichmen/*` (R-PKG)

- **R-PKG-1.** Сначала проверяется наличие функционала в `laravel-foundation` и
  `laravel-handbooks`; своё пишется только если его нет.
- **R-PKG-2.** Правки пакетов — в их репозиториях, отдельной задачей, с обратной совместимостью;
  `vendor/` не редактируется.
- **R-PKG-3.** Справочники — только через `config/handbooks.php` (`crud`, `dynamic.custom`, `enums`).
- **R-PKG-4.** Пакетные абстракции (`AbstractService`, `AbstractRepository`, `AbstractRequest`,
  `AbstractDto`, `AbstractResource`, презентеры) не дублируются своими базовыми классами.

## 10. Доступ (R-AUTH)

- **R-AUTH-1.** Авторизация — `laravel/passport`; закрытые роуты — под `auth:api`.
- **R-AUTH-2.** Публичные страницы сайта не требуют токена.
- **R-AUTH-3.** Права проверяются middleware/Policies, а не в контроллере и не в Blade.
- **R-AUTH-4.** Доступ к справочникам настраивается только в `config/handbooks.php`.
- **R-AUTH-5.** Проверка доступа выполняется до чтения/мутации, а не после.

## 11. Качество и сдача (R-QA)

- **R-QA-1.** Перед сдачей: `php -l` по изменённым файлам, `php artisan route:list`,
  `pint --test`, `phpstan analyse`, `npm run lint`, `npx vue-tsc --noEmit`.
- **R-QA-2.** Playwright-тесты запускаются на поднятом `composer dev`; отдельный веб-сервер
  для тестов не поднимается.
- **R-QA-3.** Нет отладочного кода (`dd`, `dump`, `var_dump`, `console.log`, закомментированных блоков).
- **R-QA-4.** Нет случайных реформатирований чужих файлов.
- **R-QA-5.** Вёрстка сверена с ТЗ и токенами `docs/handoff/04-tokens`; пиксельного сравнения нет (П1).
- **R-QA-6.** Коммиты и пуш — только по явной просьбе пользователя.
- **R-QA-7.** Закрытие фазы: change заархивирован **и** `docs/plan/PLAN.md` обновлён —
  статус `✅ сделано` в §3 и в заголовке фазы §4, имя заархивированного change'а в колонке
  «Change», актуальная строка «Текущая точка». Отметка ставится в той же сессии, что и
  архивация.
