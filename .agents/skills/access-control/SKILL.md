# Авторизация и доступ

Правила: `rules.md` §10, `AGENTS.md` §5.8.

**Текущее состояние проекта.** Авторизация — `laravel/passport`. В MVP все страницы
публичные, закрытых эндпоинтов нет. Справочники подключаются с middleware, когда появится
админка. Всё ниже — порядок действий на момент, когда доступ понадобится.

## 1. Что уже есть и чего нет

| Есть | Нет |
|---|---|
| `laravel/passport` для OAuth2-токенов | ролей и пермишенов (spatie/permission не подключён) |
| `auth:api` guard | `PermissionCodeEnum` и `*AccessService` |
| middleware справочников в `config/handbooks.php` | UI управления доступами |

Не придумывать несуществующие классы: если механизма нет в проекте — сначала реализуем
механизм, потом закрываем им роут.

## 2. Публичное и закрытое

| Тип роута | Где | Middleware |
|---|---|---|
| Страницы сайта (главная, заглушки) | `routes/web.php` | нет, публично |
| Справочники и enum'ы (пакет) | генерируются | `config/handbooks.php` |
| Свой JSON API | `routes/api.php` | `auth:api` + ability/Policy |

Публичная страница не должна зависеть от токена: без авторизации она рендерится так же.

## 3. Passport: подключение

1. `php artisan passport:install` — ключи шифрования и клиенты.
2. В `config/auth.php`: `'driver' => 'passport'` у guard `api`.
3. Middleware `auth:api` — на группу закрытых роутов, а не на каждый роут по отдельности.
4. Токен выдаётся через собственный контроллер (`/api/v1/auth/token`) или password grant.
5. `.env`: `PASSPORT_PERSONAL_ACCESS_TOKEN`, ключи в `storage/` — не в git.

Требования:

- Срок жизни токена задаётся осознанно (`Passport::tokensExpireIn`), refresh — тоже.
- Отзыв токена — отдельный метод, а не «удалить строку из БД руками».
- Клиентские секреты не попадают во фронтенд-бандл.

## 4. Проверка прав

Порядок выбора:

| Характер проверки | Где реализуется |
|---|---|
| «Есть ability/scopes у токена» на весь роут | middleware `auth:api` + `->middleware('scope:...')` или `can:` |
| Зависит от модели, владельца, статуса | Policy + `Gate::authorize()` в сервисе |
| Справочник | только `config/handbooks.php` |

```php
// Policy
class ProductPolicy
{
    public function update(User $user, Product $product): bool
    {
        return $user->tokenCan('products:write');
    }
}

// сервис: проверка до мутации
Gate::authorize('update', $product);
```

Требования:

- Проверка выполняется **до** чтения/мутации, бросает `AuthorizationException` (403),
  а не возвращает `false`.
- Проверки одной сущности собраны в её Policy, а не разбросаны по сервисам и контроллерам.
- Контроллер не проверяет права и не знает про токен.
- Новый ability/scope — константой в одном месте и с описанием в README API.

## 5. Справочники

- Доступ — только `config/handbooks.php`:
  `global_middleware` (обычно `['auth:api']`), `defaults.middleware.{create,update,delete,view}`,
  `*_middleware` у конкретного справочника.
- Роуты и контроллеры справочников руками не пишутся, права на них на роут не выносятся.
- `readonly => true` — когда справочник нужен только для чтения.

## 6. Проверка

```bash
php artisan route:list            # middleware на месте, роут в нужной группе
php artisan passport:keys         # если ключей нет
```

Ручные сценарии (автотестов на доступ нет):

- без токена — 401, без утечки данных;
- токен без ability — 403;
- токен с ability — успех;
- чужая сущность — отказ;
- публичная страница открывается без токена.

## Частые ошибки

- `auth:api` на публичной странице — сайт перестаёт открываться.
- Проверка прав в контроллере или в Blade-шаблоне.
- Проверка после мутации (данные уже изменены).
- `false` вместо исключения — контроллер отдаёт «успех» с пустым ответом.
- Справочник закрыт руками на роуте вместо `config/handbooks.php`.
- Секреты Passport в git или в JS-бандле.
